# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

A Salesforce DX package that implements a metadata-driven, reusable **XLSX (Excel) file reader/importer** for Apex. Admins configure Custom Metadata Types to control how uploaded `.xlsx` files (via `ContentVersion`) are parsed and turned into records, sums, or custom side effects — without writing new Apex for common cases. There is no LWC/Aura UI in this package; it is a pure Apex engine intended to be invoked from Flow (`XLSXReaderInvocable`) or directly from Apex (`XLSXProcessorService`).

Design rationale and phased build history live in `docs/XLSX_Reader_Design_Plan.md`, `docs/TASK.md`, and `docs/WALKTHROUGH.md` (these describe the original build; several gaps between that plan and the shipped code have since been closed — see Architecture below for current state). Configuration walkthroughs for specific scenarios (simple sync import, large async import, custom multi-object handlers, built-in and custom aggregation) are in `docs/EXAMPLES.md` — read that before building a new integration against this engine. A fuller, plain-language reference covering every configuration field and five worked examples is in `docs/USER_GUIDE.md`.

No `node_modules` are installed by default; run `npm install` before using any npm script.

## Commands

### Org & deployment (Salesforce CLI `sf`)
The configured default org alias is `newDevOrg` (`.sf/config.json`), so `-o` can usually be omitted.

- `sf project deploy start` — deploy all metadata to the default org
- `sf project deploy start -m ApexClass:XLSXParser` — deploy a single component
- `sf project retrieve start` — pull metadata changes back from the org

**Changing an existing Custom Metadata Type field's `type`** (e.g. Text → Picklist) cannot be deployed in place — CMDT doesn't support field type conversion, and Salesforce also won't let you delete a field that's still referenced by live Apex, even if a same-named replacement is in the same deploy. Getting the five enum-shaped fields on `XLSX_Reader_Config__mdt` (see Configuration below) from Text to real Picklists took a 4-deploy sequence: (1) deploy Apex with those fields' references stripped out, alongside no field changes, so nothing live references them anymore, (2) deploy a `destructiveChanges`-manifest deletion of the fields, (3) deploy the fields fresh with `type: Picklist` (a clean create, not a conversion, so this works), (4) deploy the real Apex again with the references restored. If this needs to happen again for some other field, that's the pattern - budget for it as multiple deploys, not one.

### Apex tests
`sf apex run test --test-level RunLocalTests --code-coverage --result-format human` runs everything; `--class-names <X> --synchronous` or `--tests <Class.method> --synchronous` for one class/method. Real test classes exist per production class (`XLSXParserTest`, `XLSXProcessorServiceTest`, `XLSXAsyncProcessorTest`, `SObjectCreatorRowHandlerTest`, `AggregateRowHandlerTest`, `XLSXReaderInvocableTest`, `XLSXDateConverterTest`) — this is a real, exercised test suite, not placeholder coverage.

Tests that drive the full pipeline rely on real deployed CMDT fixture records (`force-app/main/default/customMetadata/*.md-meta.xml`, all prefixed `Test_`) rather than constructing config in-memory, because `XLSX_Field_Mapping__mdt` lookups happen via real SOQL that can't be faked — CMDT records can be instantiated in-memory for tests that only read scalar fields (e.g. `new XLSX_Reader_Config__mdt(Hidden_Row_Handling__c = 'Exclude')`), but not for anything that queries child mapping records. `XLSXTestFixtureFactory.generateXLSXFromRows(...)` builds synthetic `.xlsx` blobs from plain `List<List<String>>` row data (inline-string cells, no shared-strings coordination needed) and optionally marks specific rows hidden or wraps the range in an Excel Table with a totals row — use it over the older `generateSyntheticXLSX(rowCount, columnCount)`, which only emits numeric cells and exists for the heap-measurement script below.

- `sf apex run --file measureHeap.apex` — anonymous-Apex heap measurement script from Phase 0 viability work (see Heap section below)

### Gotcha: fields deployed via Metadata API get zero Field-Level Security by default
Custom fields created through a metadata deploy (as opposed to Setup UI) are **invisible to every profile, including System Administrator**, until FLS is explicitly granted — SOQL and Apex both report `No such column` rather than a permissions error, so this looks exactly like the field doesn't exist. This bit `XLSX_Error_Log__c`'s fields (`Error_Message__c` etc.) — error logging silently couldn't be read by anyone until FLS was granted manually in Setup. If a test or query against a custom field mysteriously reports "no such column" despite the field clearly existing in source, check FLS before assuming a metadata/deploy bug.

## Architecture

### Processing pipeline
`ContentVersion` (uploaded file) → `XLSXProcessorService.processFiles()` (orchestrator) → `XLSXProcessorService.runPipeline()` (shared by both Sync and Async — see below) → `XLSXParser.process(blob)` (pure, zero-DML XML streaming) → `IXLSXRowHandler.processRow()` per row → `rowHandler.getResult()` → `IXLSXResultHandler.handleResult()` (the only place DML happens).

The core design principle: **the parser and row handlers never perform DML.** DML is isolated entirely behind `IXLSXResultHandler`, so parsing logic can be unit tested without database side effects and swapped independently of persistence logic.

Entry points:
- `XLSXReaderInvocable.execute()` — `@InvocableMethod`, callable from Flow.
- `XLSXProcessorService.processFiles(List<ProcessingRequest>)` — direct Apex entry point.

Sync and Async both funnel through `XLSXProcessorService.runPipeline(config, req, fileData)` — a shared, public method — specifically so the two paths can't wire the configured handlers differently again (they used to; see git history / prior review notes if curious). Every per-request iteration in `processFiles()` is individually try/caught, so one bad file, one misconfigured handler, or one hit against the 50-job-per-transaction `System.enqueueJob` limit can't take down the rest of a batch.

`XLSXAsyncProcessor.execute()` attaches a `Finalizer` (`AsyncFailureFinalizer`, private inner class) before doing anything else. Normally `logError()` catches and records everything, but `Error_Handling_Behavior__c = 'Throw Exception'` makes `logError()` deliberately re-throw (so the job shows as Failed in Setup) - without the Finalizer, that specific config combination would fail the async job with nothing written to `XLSX_Error_Log__c` anywhere. The Finalizer checks `ctx.getResult() == ParentJobResult.UNHANDLED_EXCEPTION` and writes the log directly in that case (not via `logError()` again, which would just re-throw a second time).

### Parser internals (`XLSXParser.cls`)
An `.xlsx` file is a zip archive. The parser uses `Compression.ZipReader` to pull `xl/sharedStrings.xml` (an index of deduplicated strings) and the **first sheet, resolved dynamically** via `xl/workbook.xml` → `xl/_rels/workbook.xml.rels` (falls back to the conventional `xl/worksheets/sheet1.xml` only if that resolution fails but the fallback path still exists in the archive — it does not silently guess). Both are walked with `System.XmlStreamReader` (streaming/SAX-style, not DOM) specifically to keep heap usage down. Row data is emitted to handlers as `Map<String,String>` keyed by **spreadsheet column letter** (`A`, `B`, ...), not by header name — interpreting a specific row as headers is each row handler's own responsibility. The built-in handlers key off `rowNumber == config.Header_Row_Number__c` (defaulting to `1`), not "whichever row arrives first": a title/banner row, or blank rows, above the real header row is common in real files and must not be mistaken for the header row.

`XLSXParser` also takes the `XLSX_Reader_Config__mdt` directly (constructor: `XLSXParser(IXLSXRowHandler handler, XLSX_Reader_Config__mdt config)`, config may be null) and owns three structural, config-driven behaviors that apply regardless of which row handler is in use:
- **Row threshold**: counts every physically-parsed row (including hidden/totals rows, before exclusion) against `Max_Row_Threshold__c` and throws `XLSXParserException` fail-fast once exceeded, rather than parsing an oversized file to completion just to reject it at the end.
- **Hidden-row exclusion**: reads the `hidden="1"` attribute on `<row>`; skips emitting that row to the handler when `Hidden_Row_Handling__c == 'Exclude'`.
- **Totals-row exclusion**: resolves the sheet's Excel Table (if any) via the sheet's own `.rels` file → `xl/tables/tableN.xml`, reads `ref`/`totalsRowCount`, and skips the last row of the table range when `Totals_Row_Handling__c == 'Exclude'`. Scoped to one table per sheet (the common case); multiple tables on one sheet aren't disambiguated.

The `rowNumber` handed to `IXLSXRowHandler.processRow()` is always the row's literal Excel row number (from the `<row r="N">` attribute), never a "rows seen so far" counter — a row that's skipped upstream (hidden-row exclusion, or a genuinely blank row that emits no `<c>` cells at all and is therefore never sent to the handler) does not shift the numbering of the rows after it. This is what makes `Header_Row_Number__c` meaningful: setting it to `5` means literally Excel row 5, regardless of what happened to rows 1-4.

`XLSXParser.peekUncompressedSheetSize(Blob)` (static) resolves the sheet and returns its **uncompressed** size from the zip's central directory without extracting/decompressing content — this is what Sync/Async routing uses (see Heap section), not `ContentVersion.ContentSize` (compressed).

Before extracting `sharedStrings.xml` or the sheet, `process()` also checks each entry's uncompressed size against `assertSafeToExtract()` — a hard ceiling at 40% of `Limits.getLimitHeapSize()` (so it adapts to sync vs. async automatically) — and throws before decompressing anything over that. This exists because the Auto-routing peek above is *only* consulted when `Execution_Mode__c = Auto`; an explicit `Sync` or `Async` config has no other pre-extraction size check, so without this a small, highly-compressed file could still force a large decompression. `assertSafeToExtract` is `@TestVisible` specifically so tests can exercise the threshold logic directly with a fabricated size rather than needing to actually materialize a heap-blowing fixture (which risks failing the test for the wrong reason - heap exhausted during fixture generation itself, not the gate under test).

### Extensibility model
Turning a row into a persisted outcome is two independent, separately-configured roles on `XLSX_Reader_Config__mdt`:
- **`Row_Handler_Class__c`** — an `IXLSXRowHandler` that builds an in-memory result from parsed rows.
- **`Result_Handler_Class__c`** — an `IXLSXResultHandler` that persists that result.

Both are dynamically instantiated via `Type.forName(...).newInstance()` and **independently** — even if both fields name the same class, you get two separate instances (data must flow through `getResult()` → `handleResult(parsedResult)`, not shared instance state). Misconfiguration (blank, unresolvable class name, or a class that doesn't implement the required interface) throws immediately rather than silently falling back to a no-op — there is no mock/stub fallback in the shipped code. See `docs/EXAMPLES.md` for the full set of built-in and custom handler pairings.

Built-in row handlers: `SObjectCreatorRowHandler` (maps rows to SObjects using `XLSX_Field_Mapping__mdt` records with `Aggregate_Function__c` blank; routes Date/Datetime target fields through `XLSXDateConverter` when the raw cell is a numeric Excel serial; per-field conversion failures are recorded via `IXLSXWarningSource.getWarnings()` rather than silently dropped) and `AggregateRowHandler` (SUM/COUNT/MIN/MAX/AVERAGE over one column, per the single `XLSX_Field_Mapping__mdt` row for that config with `Aggregate_Function__c` set). Both cache `config.Header_Row_Number__c` (as `headerRowNumber`, defaulting to `1`) in `initialize()` and compare it against the real Excel row number on every `processRow()` call — this is what lets a table start anywhere in the sheet rather than only at row 1; rows before the header row are naturally no-ops since the column-to-field map is still empty when they arrive, so no separate "skip these rows" logic was needed.

**Numeric target fields in `SObjectCreatorRowHandler.convertValue()`**: `SObject.put()` does not implicitly coerce a `String` into a `Decimal`/`Integer`-backed field — it throws `Illegal assignment from String to Decimal` (or `...to Integer`) unconditionally, even for a perfectly well-formed numeric string. `convertValue()` therefore special-cases `Schema.DisplayType.CURRENCY`/`PERCENT`/`DOUBLE`/`INTEGER` the same way it already special-cased dates: parse with `Decimal.valueOf(rawValue)`, and for `INTEGER` specifically call `.intValue()` (truncates toward zero, same convention `FieldWriteBackResultHandler.coerceForTargetField()` already uses for the aggregation path). This was written as **explicit `if`/`else` returns, not a ternary** — `fieldType == INTEGER ? parsed.intValue() : parsed` silently widens the `Integer` branch back into a `Decimal` (ternary operand-type unification promotes both branches to a common numeric type before boxing to `Object`), which then fails `put()` with the exact same `Illegal assignment from Decimal to Integer` error being worked around. Caught this via live anonymous-Apex probing against the connected org rather than by reasoning about it — if this method needs touching again, don't reintroduce a mixed-type ternary here.

`AggregateRowHandler`'s math runs on Apex `Decimal` (arbitrary-precision, not binary floating point), so SUM/MIN/MAX never accumulate float rounding drift. `AVERAGE`'s `/` division is *not* rounded to a small fixed scale — `100 / 3` yields `33.3333333333333333333333333333333` (31 digits), confirmed empirically. `FieldWriteBackResultHandler` writes that `Decimal` straight through for Currency/Percent/Double target fields (Salesforce does not round to a Number/Currency field's declared *scale* on write via API — that scale is a display format, not a storage constraint; a Decimal can be written with far more precision than the field displays) and via `.intValue()` (truncation, not rounding) when the target is a genuine Integer field.

Built-in result handlers: `DatabaseInsertResultHandler` (chunks into 200-record batches via `Database.insert(chunk, false, AccessLevel.USER_MODE)` for partial success — not one unchunked all-or-nothing insert — and throws a summary if any chunk had failures) and `FieldWriteBackResultHandler` (writes an `AggregateRowHandler.AggregateResult` onto a field on the request's `relatedRecordId`; pairs with `AggregateRowHandler`).

### Configuration (Custom Metadata Types)
- **`XLSX_Reader_Config__mdt`** (parent, looked up by `DeveloperName`): `Execution_Mode__c` (Picklist: `Sync`/`Async`/`Auto`), `Async_Threshold_Bytes__c`, `Max_Row_Threshold__c`, `Row_Handler_Class__c`, `Result_Handler_Class__c`, `Error_Handling_Behavior__c` (Picklist: `Log Error`/`Throw Exception`/`Fail Silently`), `Empty_Result_Behaviour__c` (Picklist: `Zero`/`Null`/`Skip` — only consulted by `AggregateRowHandler`; blank means "use the function-appropriate default"), `Hidden_Row_Handling__c`, `Totals_Row_Handling__c` (Picklist: `Include`/`Exclude`), `Header_Row_Number__c` (Number, blank defaults to `1` — the literal Excel row number holding the column headers, for tables that don't start at the top of the sheet; consumed by both built-in row handlers, not by `XLSXParser` itself).
- **`XLSX_Field_Mapping__mdt`** (child, via `Config__c` metadata relationship): `Excel_Column_Header__c`, `Target_SObject__c`, `Target_Field__c`, `Aggregate_Function__c`. A mapping row with `Aggregate_Function__c` blank is a record-creation column mapping (consumed by `SObjectCreatorRowHandler`); one with it set is an aggregation spec (consumed by `AggregateRowHandler`/`FieldWriteBackResultHandler` — in that case `Target_Field__c` means the field on `relatedRecordId` to write into, and `Target_SObject__c` is unused but still required by the field definition).
- **`XLSX_Error_Log__c`** (custom object, not CMDT): `Error_Message__c`, `Stack_Trace__c`, `Related_Record_Id__c`, `File_Name__c`, `Related_Record_Link__c` (formula: `HYPERLINK()` wrapping `Related_Record_Id__c`, since that field is deliberately polymorphic-by-convention Text rather than a typed Lookup, so it can't get click-through for free). `sharingModel` is `Read` (Public Read Only) — deliberately not `ReadWrite`, so error/audit evidence isn't casually editable. Remember the FLS gotcha above if these fields ever look inaccessible.

`Execution_Mode__c`, `Error_Handling_Behavior__c`, `Empty_Result_Behaviour__c`, `Hidden_Row_Handling__c`, and `Totals_Row_Handling__c` are real restricted Picklists (see the CMDT field-type-conversion note under Commands above for how that migration was actually done). `Row_Handler_Class__c`/`Result_Handler_Class__c` are necessarily plain `Text` — they hold arbitrary Apex class names, which can't be a fixed picklist. For the five Picklist fields, Apex still branches on the literal string values (`config.Execution_Mode__c == 'Async'`, etc.) rather than an enum type, same as before the conversion — grep the `.cls` files for a field name to find the exact set of values it currently branches on.

### Heap / governor-limit constraints
This is the reason the Sync/Async/Auto routing exists at all. `Blob.toString()` (turning the extracted sheet XML into a `String` for `XmlStreamReader`) is the peak heap spike, because it briefly holds both the raw blob and the expanded string at once. Phase 0 measured this empirically with `XLSXTestFixtureFactory.generateSyntheticXLSX()` and `measureHeap.apex`: a 25,000-row file costs ~5.91 MB against the 6 MB sync heap limit. Defaults keep a ~40% headroom buffer: `Max_Row_Threshold__c` defaults to 10,000 rows (sync), `Async_Threshold_Bytes__c` defaults to ~500 KB, above which `Execution_Mode__c = Auto` routes to `XLSXAsyncProcessor` (Queueable, 12 MB heap limit) instead of running inline. The Auto routing check compares against `XLSXParser.peekUncompressedSheetSize()`, not `ContentVersion.ContentSize` — compressed size is a poor proxy for the actual heap-risk metric (highly-repetitive tabular data can compress 5-20x, so a file that's genuinely heap-risky can look tiny while still zipped).

### Date handling (`XLSXDateConverter.cls`)
Converts Excel's serial-number dates to Salesforce `Datetime`/`Date`, anchored to GMT, and explicitly reproduces Excel's fake 1900-leap-year bug (serial 60 = Feb 29 1900, which doesn't exist — mapped to Feb 28 1900). Called from `SObjectCreatorRowHandler` whenever a mapped target field describes as `Schema.DisplayType.DATE`/`DATETIME` and the raw cell value parses as numeric.
